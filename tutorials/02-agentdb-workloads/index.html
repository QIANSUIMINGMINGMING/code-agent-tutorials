01

什么是 Agent-Native Workload？

“让 Agent 能调用系统”只增加了一个接口；真正的 workload 变化，是相邻执行开始共享状态、反馈与未完成工作。

MULTI-ROUND

一轮的输出，成为下一轮输入

反馈延迟、状态写回和停止条件都会改变后续行为。

CORRELATED

相邻 Candidate 不是独立样本

它们通常围绕同一 Anchor，只改变少量代码、证据或约束。

REVISABLE

模型输出只是 Proposal

只有经过 evaluation、validation 和 commit，变化才成为新状态。

Agent-native 的系统机会来自一个简单变化：优化单位从“一次调用”变成“一条相关的状态转移轨迹”。
02

从 Alpa 的 Strategy Search 到 FlexEva

Alpa 将分布式训练优化为：给定计算图和集群，在预定义的 inter-/intra-operator parallelization strategy space 中生成并选择执行计划。FlexEva 的出发点是，Code Agent 不再只在这个空间内选 plan，而会直接修改 source。

FLEXEVALightweight Emulation for Closed-Loop ML Workload Optimization with Resilient Anchor State · EuroSys 2027 Submission
FIXED INPUT

计算图与集群配置已知

优化器接收一个确定的 computational graph 和 device cluster，而不是任意修改后的程序。

BOUNDED STRATEGY SPACE

Candidate 是 Parallelization Plan

搜索空间由 inter-operator 与 intra-operator parallelism 的组合预先定义。

AGENTIC SHIFT

Code Agent 直接改变 Source

routing、control flow、communication 或 operator implementation 都可能变化，candidate 不再只是 strategy assignment。

Alpa 问的是：已知 Strategy Space 中哪个 plan 最好？ FlexEva 问的是：任意 source mutation 之后，哪些 evaluator evidence 仍可复用，哪些必须刷新？

04 · 总

AgentDB 的大目标：把整个 Agentic Loop 变成 Query Processing

一个大任务通常不是一次 LLM call 就能完成，而是一个 Human–Agent pair 持续交互、调用工具、观察结果并修正计划的多轮过程。AgentDB 用一个真实 DBMS 管理这整个过程。

TASK = QUERY

一个大任务是系统要完成的 Query

Human 给出目标，并在执行过程中持续补充反馈与修正。

LOOP = PLAN

多轮交互是一条自适应执行计划

每轮根据当前 State 与 Trace 重新投影，再执行 LLM 和 Tool 算子。

TASK = TRANSACTION

整个任务才是 Transaction

事务从任务开始一直保持 open，只在整体完成并验证后 commit。

最核心的抽象只有一句：一个 Task 是一条长期 Transaction；Human–Agent Loop 是它的递归 Query Plan。

一轮只是 Transaction 内部的 Plan Fragment

把 loop 交给真实 DB 管理，关键不是换一个比喻，而是让组装 prompt、调用 LLM、操作工具、记录 trace 和更新 state 都成为可组合、可替换、可优化的算子。

Round 和 Transaction 的关系是：Round 是重复执行的 plan fragment；Task 才是 transaction。
外部副作用：邮件、部署等不可回滚操作仍需要 authorization、idempotency 或 compensation；把它们表示成算子，不会自动获得 ACID 语义。
06 · 分

确定完整边界之后，
再看 Related Work

已有系统分别优化 semantic query、agent-facing data system、harness、memory、serving 或 transaction。现在可以精确比较：它们覆盖 AgentDB 计划中的哪些子算子，又把哪些跨算子决策留在边界之外。

AI / DATA QUERY SYSTEMS

PromptFirst · Palimpzest · TAG · Pneuma

已有prompt、semantic operator、AI pipeline 与 information need 成为数据系统对象。
边界主要优化声明式 pipeline 或数据接口，而非持续演化的长期 Agent Task。
AGENT-FIRST DATA SYSTEMS

Agent-First

已有识别 tireless speculative agents 对数据系统带来的规模、冗余和异构压力。
边界核心对象是面向 Agent 优化 data system，而不是 Agent workload plan 本身。
HARNESS + MEMORY

Codex / Claude Code / SWE-agent · MemGPT / Graphiti / Mem0

已有orchestration、tool use、recall、context management 与 personalization。
边界这些能力可以成为 physical operators，但没有自动形成跨算子的 workload optimizer。
SERVING + PROVENANCE + TXN

Pie-style serving · workflow provenance · context exchange · transactional runtimes

已有模型调用内部优化、轨迹记录、上下文交换或局部 validate/commit/recover。
边界单独机制不决定 projection、model/tool placement、validation、reuse 与 persistence 的联合计划。
缺少的不是某一个 feature，而是一个共同边界：把整个长期 Task 当作 Transaction，并联合管理 State、Trace、Projection、LLM 与 Tool operators。
Positioning boundary：AgentDB 不以 memory、transaction、retrieval 或 workflow optimization 中任何单点作为 novelty；研究重点是它们在整个 Human–Agent Loop 中的联合规划。

统一数据库的价值 I：Cross-Operator Optimizer

同一个 Task 可以拥有多个 execution plans。只有把 Project、LLMCall、ToolCRUD、Trace 与 FinalValidate 放进同一计划，系统才能比较整个任务的端到端成本与质量。

LOGICAL WORKLOAD
RunTask(task, state, full_trace, budget)
PLAN A · HISTORY DRIVEN

把所有历史重新交给强模型

RawHistory→StrongModel→FullTest

实现简单，但重复探索、上下文干扰和昂贵 validation 可能同时发生。

PLAN B · TRACE AWARE

保留 Full Trace，每轮构造 Task-Specific Projection

FullTrace→Project→ModelTier→TargetedTool→ValidateTask

数据库保留全部事实，optimizer 只决定当前调用真正需要看到什么。

PROJECTION

本轮看哪些 State / Trace？

从完整记录中抽取与当前 Task step 相关的信息。

PLACEMENT

何时调用 Model / Tool？

决定顺序、model tier、reasoning effort、tool route、fork/join 与 budget。

VALIDATION

整个 Task 何时完成？

选择 targeted test、full test、human review，或继续下一轮。

TotalCost = model_tokens + model_latency + model_price + tool_latency + validation_cost + stale_risk + conflict_risk − reuse_value

CHALLENGE

Semantic Selectivity

很难预估哪些 state 真正会改变答案。

CHALLENGE

动态统计

State、模型、工具和 Task 持续变化。

CHALLENGE

统一数据库的价值 II：整个 Task 才是 Transaction

事务从 Human 提出大任务时开始，在很多轮 Human–Agent interaction 中持续保持 open，直到最终结果与状态被整体验证后才 commit。

BEGIN

Begin Task Transaction

保存 Task、初始 State 与第一条 Human input。

→
MANY ROUNDS

Human–Agent Loop

Project、LLM、Tool、AppendTrace 与 UpdateState 反复执行。

→
FINAL ONLY

Validate & Commit

Human–Agent pair 确认整个 Task 完成后提交最终结果与 State。

↺ TASK NOT DONE → Append / Checkpoint / Continue
✓ TASK DONE → FinalValidate / COMMIT TASK TRANSACTION
SYSTEM ADVANTAGE

Durable Progress 不等于 Commit

每轮都可以保存 Trace、State 与 checkpoint，但逻辑上的 Task Transaction 仍然 open。

SYSTEM ADVANTAGE

Human Feedback 是事务输入

澄清、否定、验收和目标修正都会进入同一 Task Transaction，而不是被拆成无关请求。

CHALLENGE

Long Transaction

一个任务可能跨小时、会话甚至多位用户。

CHALLENGE

External Effects

邮件、部署和 API 写入未必可以 rollback。

CHALLENGE

Concurrent State

长任务执行期间，底层代码与数据仍可能变化。

CHALLENGE

Human Wait

事务必须跨越澄清、审批、修正与最终验收。

AgentDB 的事务对象不是一条 message 或一次 model call，而是Human 与 Agent 为完成同一个大任务而共同经历的整个 Loop。

Derived View，不是 Base State

10 · 分

Compaction：Full Trace 最好，
但 Context 放不下

Full Trace 是最好的数据库 base state：它保留全部信息、表示失真为 0。但它未必是最好的 model input，因为固定 context budget 无法容纳无限历史。真正的问题是：为当前调用构造什么有损 view？

RATE–DISTORTION

完整 Trace 是 Zero-Distortion Baseline

H = Full Trace
C = H ⇒ D(H,C) = 0

不压缩时没有表示损失，但需要最高 rate。给定 context budget B，系统只能选择满足 |C| ≤ B 的有损表示。

TASK-RELATIVE DISTORTION

“丢什么”取决于下一次调用

Cq = f(H,q)
Rq(D) = min I(H;Cq)
s.t. E[dq(H,Cq)] ≤ D

q 表示当前任务步骤。不同 q 对历史细节的重要性不同，因此不存在一个对所有未来调用都最优的永久 summary。

关键区分：Full Trace 是最好的存储真相；Task-Specific Projection 才是有限 context 下的模型输入。
CURRENT HARNESS PATTERN

对 Active Context 的毁灭性替换

旧 history 被 summary / compaction item 取代。即使 rollout 记录仍存在，被省略细节也不会自动重新进入下一次 model input。

AGENTDB ALTERNATIVE

Full Trace + Query-Time Projection

数据库始终保存完整 Trace；每次 LLM call 根据当前 Task 生成新的 view，并保留返回原始记录的指针。

Theory boundary：Rate–distortion 并不证明某个具体 summarizer 最优；它证明“最优压缩”必须相对于显式 distortion measure 定义。Information Bottleneck 进一步把 relevance 定义为表示对目标变量保留的信息。

统一 DBMS Boundary：从 Reuse / Refresh 到 Projection

FlexEva 管理已知 mutation 之后的 reuse / refresh；AgentDB 进一步面对一个长期 Task：数据库保存完整 State 与 Trace，并为 Human–Agent pair 的每一轮生成 task-specific projection。

DimensionFlexEvaAgentDB
Base state一个程序版本对应的 evaluator stateTask + State + Full Trace
Change已知 source-level mutationHuman feedback、LLM output、tool result
Primary question哪些 evaluator state 可以 reuse，哪些必须 refresh？本轮看什么，以及整个 Task 何时可以 commit？
Correctnessfeedback fidelityTask completion 与最终 State correctness
FLEXEVA LESSON

Trajectory 内部存在可利用的增量结构

当 mutation、partition 与 lineage 可识别时，每轮全部重做可以转化为 reuse 和 selective refresh。

AGENTDB EXTENSION

复杂 State 与 Full Trace 让 Projection 成为前置问题

系统必须根据当前 Task step 决定本轮看什么，同时保留完整 Trace，直到整个 Human–Agent Loop 最终 commit。

FlexEva 说明如何增量维护一个已知 evaluator loop；AgentDB 进一步研究：如何用 Full Trace 支撑 task-specific projection，并把整个 Human–Agent Loop 作为一条长期 Transaction 管理。
