Agent 如何工作

基于 Codex 的实现分析

Agent Loop 就像人做事：先了解当前工作环境，采取一步行动，观察环境发生了什么变化，再据此决定下一步，如此反复直到任务完成。

01

Agent Loop 的最小可执行骨架

ReAct 给出“想一步、做一步、看结果”的节奏；Agent runtime 把它实现为多次模型调用和真实环境交互。

MINIMAL AGENT LOOPPSEUDOCODE
state ← initialize(user_request)
while true:
    view ← build_context(state)
    # Reason
    decision ← LLM(view, tools)
    if decision is Final:
        return decision.answer
    # Action proposal
    action ← decision.tool_call
    observation ← Runtime.execute(action)
    state ← update(
        state, action, observation
    )

state 是 runtime 当前记录的任务状态；view 是这次模型调用看到的内容；observation 是执行动作后捕获的结果。

模型负责提出下一步；runtime 负责让动作发生、捕获结果，并带着新状态再次调用模型。
02

把 Agent Loop 写成状态转移

LLM 不直接读取或修改工作世界；它读取 runtime 构造的 view，产生 proposal，世界转移由 runtime 执行。最小伪代码中的每一行，都对应一个明确的状态转移算子。

FORMAL STEP · RESEARCH ABSTRACTION
(Wt, St) → (Wt+1, St+1)
Pt = πt(St)
view ← build_context(state)
qt = M(Pt)
decision ← LLM(view, tools)
qt = Final(yt) or qt = Act(at)
if Final: return; else: tool_call
(Wt+1, ot) = ExecuteΓₜ(Wt, at)
observation ← Runtime.execute(action)
St+1 = Reduce(St, qt, ot)
state ← update(state, action, observation)

SYSTEM OBJECTS · t = MODEL STEP

Wt
真实工作世界：文件、进程、测试、网络服务与其他参与者。
St
runtime state：目标、历史、证据、权限、计划和控制信息。
Pt
model-visible view：instructions、input、tools 与输出约束。
qt
模型 proposal：最终答案 yt 或候选 action at。
ot
有限 observation：stdout、退出码、diff、错误或工具结果。

SYSTEM OPERATORS

πt构造本次 view
M一次 LLM 调用
ExecuteΓ受控执行 action
Reduce写回下一步 state
只有 M 是 LLM 调用；πt、ExecuteΓ、Reduce 和循环控制都是 runtime 程序。
03

Agent Loop 的两个状态接口

每轮交互对 state 只做两件核心事情：调用前读出一个有限视图，调用后把模型输出与新的世界证据写回。

project_state : St → Pt

选择、规范化并限制一次调用可见的 state。完整 state 中的控制信息、原始证据和外部世界不会自动全部进入 prompt。

update_state : (St, qt, ot) → St+1

把 proposal 与对应 observation 一起写回，保留 call/output 关系与 provenance；它不是对一段 stdout 的盲目 append。

Agent 的核心不是不断给 LLM 追加聊天记录，而是在反复执行一次 state read 和一次 evidence write。
04

Codex 如何构造一次 LLM Call Input

Codex 中没有一个单独的 project_state()。这个抽象由 request snapshot、context materialization、history normalization 与 prompt assembly 共同实现。

关键一致性边界：每个 model step 只捕获一次 StepContext，使注入的 context、向模型公开的工具，以及随后执行工具时使用的环境来自同一个 request-scoped view。

// and tool calls share one request view.

let input = sess.clone_history().await
    .for_prompt(&model.input_modalities);
session/turn.rs · build_promptabridged source
Prompt {
    input,
    tools: router.model_visible_specs(),
    parallel_tool_calls: model.supports_parallel_tool_calls,
    base_instructions,
    output_schema,
}
input[] 不是完整 state，也不是 LLM 在一次调用里持续 append 的数组。它是 runtime 从当前 ContextManager 取得并规范化的 snapshot；工具定义则由同一个 StepContext 单独投影后再与之汇合。

命名边界：Codex 源码中的 WorldState 管理 environment、AGENTS、apps、plugins 等模型可见环境片段的 typed snapshot/diff。它只是本文 St 中为 projection 服务的一部分，不是完整外部工作世界 Wt。

05

Codex 如何把 World Observation 写回 State

一次工具交互不是“执行完成后 append 一段输出”。Codex 先记录模型提出的 tool call，再执行工具，最后把处理后的 observation 作为第二条记录写入 model-visible state。

stream_events_utils.rs · write proposalabridged source
record_completed_response_item(..., &item).await;

let tool_future = ctx.tool_runtime
    .handle_tool_call(call, cancellation_token);

output.needs_follow_up = true;
session/turn.rs · write observationsource
let response_item = response_input.into();
sess.record_conversation_items(
    &turn_context,
    std::slice::from_ref(&response_item),
).await;
PostToolUse 的精确语义：工具已经完成后，hook 可以拒绝或替换“给模型看的结果”，但不能撤销已经发生的文件或进程副作用。因此 world effect、raw result 与 model-visible observation 必须分开建模。
只有被转换并记录的 observation 才会进入下一次 projection。Codex 在写入 function output 时应用 truncation policy；下一次 for_prompt() 还会检查 call/output 配对并移除 orphan output。
06

Feature 的演化，是 State Scope 的扩张

从 ReAct 到 MCP、Skill、Subagent 与 Hooks，变化的重点并不是 LLM call 本身，而是 runtime 开始维护更丰富的 World interface、procedure、trajectory 和 lifecycle。

2022 · ReAct 2023 · Function Calling 2024 · MCP 2025 · Codex 2025 · Agent Skills 2026 · Harness Engineering
趋势不是“把更多文字塞进 Prompt”，而是让 runtime 的 State 能够引用、观察、组织和控制更复杂的真实世界；每次模型调用仍只看当前任务需要的投影。

边界：State 不等于 World 的完整副本。它更像 World 的局部模型与 control plane：保存 capability、observation、证据、约束、分支和重新观察世界的 handle。

State 变丰富，不等于 Prompt 变长。完整 trace、远程 capability、child trajectory 与 checkpoint 可以留在 runtime；本轮 LLM call 只接收它需要的 materialized view。

MCP：把远程 CI 接进 Agent Loop

任务：“远程 CI 有一个失败测试，请定位原因、修复并验证。”基础 Agent 只能读取本地仓库；加入 MCP 后，runtime 可以发现远程 CI 工具，并把结果作为带来源的 observation 写回 State。

09

Subagent：把一条 State 序列变成 State Graph

父 Agent 已经通过 MCP 获得 CI failure。它把“读取日志与相关测试、定位根因，不修改文件”交给一个 child；child 在独立 thread 中运行同一个 Agent Loop，最后只把有边界的结果与证据返回父线程。

SUBAGENT EXTENSIONCONCEPTUAL DIFF
while true:
    view ← build_context(state)
    decision ← LLM(view, tools)
    action ← decision.tool_call

    if action.name == "spawn_agent":
        child_state ← fork_state(
            parent=state,
            goal=action.task,
            history=select_history(
                state, action.fork_turns
            )
        )
        child_id ← Runtime.spawn(
            AgentLoop(child_state)
        )
        state.agent_graph.add(child_id)
        result ← Runtime.wait(child_id)
        state ← merge_child_result(
            state, result.evidence
        )
        continue

    observation ← Runtime.execute(action)
    state ← update(state, observation)

spawn_agent 可以仍表现为一次 tool action；特殊之处是 handler 启动了另一份 loop，并为它建立独立 State 与 lineage。

WHY READ-ONLY FIRST?

先隔离探索噪声，再讨论写冲突

read-heavy exploration、tests、triage 和 log analysis 最容易独立。若父子同时改同一仓库，还需要 worktree、world-delta validation 与 conflict policy；这不是“多开一个模型”自动解决的。

不要把 merge 简化为 transcript append：child 可能读了大量日志、执行了多轮搜索。父线程真正需要的通常是结论、file reference、evidence 与未解决问题；共享 World 的修改则必须单独验证。
10

Harness、Hooks 与 Loop Engineering：谁决定 State 怎样变化？

三个词处在不同层次：Harness 是运行循环的程序；Hooks 是可插入的生命周期边界；Loop Engineering 是对 projection、execution、verification、retry、compaction、delegation 和 stop policy 的整体设计。

HARNESS

可执行的 Runtime 骨架

真正维护 State、调用模型、路由工具、捕获 observation 并决定是否继续。

HOOKS

生命周期 Extension Points

允许外部脚本在特定边界注入 context、修改输入、阻止动作或请求继续。

LOOP ENGINEERING

State Transition 设计学

决定状态怎样投影、验证、分支、压缩、恢复和停止，不等于某一个 hook 或产品 feature。

BEFORE TURN

Session / Prompt

SessionStart、UserPromptSubmit 可以注入 additional context 或提前阻止。

BEFORE ACTION

PreToolUse

检查或更新 tool input；PermissionRequest 可以给出授权决定。

AFTER ACTION

PostToolUse

处理 model-visible response；不能撤销已经发生的 World effect。

CONTEXT LIFECYCLE

Pre / PostCompact

在 context 重写边界执行记录、验证或停止 policy。

BEFORE COMPLETION

Stop / SubagentStop

最终消息只是停止候选；hook 可以注入 continuation fragment。

POLICY-WRAPPED LOOPPSEUDOCODE
input ← session_and_prompt_hooks(input)
state ← record_input(state, input)

while true:
    view ← build_context(state)
    decision ← LLM(view, tools)

    if decision is Final:
        outcome ← stop_hooks(state, decision)
        if outcome requests continuation:
            state ← record(outcome.context)
            continue
        return decision.answer

    action ← pre_tool_hooks(
        decision.tool_call, state
    )
    observation ← Runtime.execute(action)
    observation ← post_tool_hooks(
        observation, state
    )
    state ← update(state, observation)
    state ← compact_hooks_if_needed(state)

11

回到最初的 Loop：Feature 到底加在哪里？

把所有功能放回第一页的伪代码，会发现最小循环没有被推翻。扩张发生在模型调用之前、之后和分支处；中间那行 LLM(view, tools) 基本保持稳定。

ONE LOOP · SIX EXTENSION POINTSFINAL PSEUDOCODE
state ← initialize(
    request, memory, checkpoint, policy
)
tools ← local_tools ∪ discover_mcp_tools()

while true:
    skills ← select_relevant_skills(state)
    view ← build_context(state, skills)
    decision ← LLM(view, tools)

    if decision is Final:
        if completion_policy(state, decision):
            return decision.answer
        state ← record_missing_obligation(state)
        continue

    action ← before_action_hooks(
        decision.tool_call, state
    )

    if action is spawn_agent:
        observation ← AgentLoop(
            fork_state(state, action.task)
        )
    else if action is MCP:
        observation ← MCP.call(action)
    else:
        observation ← Runtime.execute(action)

    observation ← after_action_hooks(
        observation, state
    )
    state ← update_and_validate(
        state, action, observation
    )
    state ← compact_or_checkpoint(state)
STABLE CORE

Model Call 几乎不变

它仍然接收一次 projection 和一组 tool schemas，然后产生 final 或 action proposal。

BEFORE MODEL

State preparation 变复杂

恢复 memory、发现 MCP tools、选择 Skill、裁剪 history 与构造本轮 view。

AFTER MODEL

Transition runtime 变复杂

授权、路由、subagent recursion、observation shaping、validation 与 checkpoint。

COMPLETION

Final 只是停止候选

测试证据、未完成 obligation、hook 与 completion policy 共同决定是否真正结束。
