01
Codex implementation

Skill 的 Prompt 到底怎样装配

Codex 不会在启动时把所有 SKILL.md 正文塞进上下文。实现上存在两个不同阶段：先用 metadata 形成可选目录，再加载被选中的 Skill 正文。

一句话概括实现：Skill = catalog projection + selection + body loading + resource tool calls。 “Skill 已安装”“Skill 已出现在目录”“Skill 正文已经进入本轮 Prompt”是三种不同状态。

第一层：Host 发现 Skill，但只投影 metadata

Codex 从 repo、user、admin、system、plugin 等 roots 扫描 SKILL.md。Loader 在 host 侧读取文件，解析 frontmatter 中的 name 与 description，并可合并 agents/openai.yaml 中的 invocation policy、tool dependencies 和界面信息，形成 SkillMetadata snapshot。

这个阶段“运行时已经读过文件”不等于“模型看到了正文”。进入初始 Prompt 的只是每个可隐式调用 Skill 的名称、描述和 locator。

第二层：Catalog 进入 developer message

[developer]
<skills_instructions>
## Skills
### Available skills
- paper-repro: Reproduce a paper with anchored claims.
  (file: /.../paper-repro/SKILL.md)
### How to use skills
...selection and progressive-disclosure instructions...
</skills_instructions>

build_available_skills 为这份目录设置预算：默认最多使用模型 context window 的 2%；如果 context window 未知，则使用 8,000 字符。预算不足时先缩短 description，仍不足才省略部分目录项并发出 warning。Skill 正文不计入这份目录预算。若 allow_implicit_invocation: false，该 Skill 不出现在隐式选择目录中，但仍可被显式选择。

第三层：显式调用与隐式调用走不同时间线

显式：本轮首次采样前装入

用户输入 $skill-name、带 locator 的 mention，或 UI 生成结构化 UserInput::Skill。Runtime 解析 mention，按精确 path 或当前 catalog 的 name-resolution 规则选中 Skill、读取正文，然后把它包装成 user-role contextual message。

隐式：模型先看 catalog，再决定读取

首次采样只有 description 与 locator。模型依据 description 决定使用后，通过文件读取或 skills.read 获得正文；读取结果成为 tool observation，影响后续采样。

[developer]  <skills_instructions> catalog + usage rules </skills_instructions>
[user]       请使用 $paper-repro 复现 Maya
[user/contextual]
<skill>
  <name>paper-repro</name>
  <path>/.../paper-repro/SKILL.md</path>
  ...SKILL.md body...
</skill>
→ history.for_prompt(...) → first LLM sample
Implementation seam 当前源码同时保留 core 的 host-skill injection 与 app-server 的 skills extension。二者都使用同样的 <skill> user-role 包装；app-server extension 对自动注入的 main prompt 设置 8,000-byte 上限并在截断时告警，随后仍可通过对应资源读取机制继续读取。

第四层：references、scripts 与 assets 不会自动进入 Prompt

SKILL.md 只负责告诉模型下一步应读取或运行什么。相对引用由 Skill 所在目录解析；随后发生的文件读取、脚本执行或 asset 复用都是工具动作。它们的输出以 tool result 写回 conversation history，才成为后续 Model View 的一部分。

Part 1 · Takeaway

先问“这轮 Agent 看见了什么”，再问“模型为什么做错了”

先分清用户消息、Skill catalog、Skill 正文和 tool result，再把最终 completion 中的论文信息与模型补全分开。

  • Prompt 是当前 Model View，不只是用户输入框。
  • Skill 的 catalog、正文和资源结果在不同阶段进入 Prompt。
  • PDF 文件不等于模型已看到全文；本例真正进入后续调用的是 pdftotext 输出。
  • 最终回答中的具体 schema、policy、formula 和 API 需与论文 tool result 分开看。
03
Common distribution prior

Prompt 只写偏离常见分布的部分

LLM 不会天然知道你的机器和工作习惯。缺少信息时，它会用训练中更常见的任务与用户补全当前世界。

普通个人电脑的 CPU 核数远低于数百核。因此面对计算任务，模型容易采用保守的低并发、小样本或串行策略。这在常见环境里合理，在异常强的机器上却会浪费资源。

常见分布

核心和内存有限；过度并发容易拖慢交互或耗尽资源。

合理默认：保守并发，先小规模试跑。

模型自动补全

如果 Prompt 和环境规则都没有说明，模型不会凭空知道用户拥有一台大工作站。

结果：方案可能正确，但资源策略不适合你。

全局 AGENTS.md 如何纠正常见先验

  • CPU 密集任务先检查 CPU 和内存资源。
  • 按内存和任务约束，使用大部分或全部实际可用核心。
  • 优先向量化、分区、批处理和可恢复的全量执行。
  • 采样和缩小数据只能叫 smoke test，不能冒充完整结果。
SAME TASK PROMPT
“对全量数据完成特征生成并跑完整实验。”

没有全局规则时，模型容易按普通电脑设计低并发流程；装配了这段持久规则后，同一句任务会先检查真实资源，再决定 worker、batch 和 partition 数量。

不用特别写

任务规模很小，或者并行度不会改变结果、成本与完成时间。

同一例子：只跑一个小样本 smoke test。

需要覆盖默认先验

任务明显依赖一个偏离常见分布的本地事实。

同一例子：要求全量运行，并真正利用 256 个逻辑 CPU。

写在哪里 长期成立的例外写进全局 AGENTS.md，不必在每个 Prompt 里重复；只对本次成立的例外，例如“本次最多使用 64 核”，写进当前 Prompt。
如果遗漏某条信息会让模型按“普通情况”做出错误执行策略，就明确写出来；否则让 Prompt 保持简短。 PROMPT THE DEVIATION, NOT THE DEFAULT
